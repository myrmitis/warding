The harness router (warding route) sends a spawned subagent to another installed harness: flat-rate plan quota before metered spend, the kind of task, and a cooldown after a usage limit or a failed login. It picks a harness and never forwards provider traffic. Registered · unverified.

The order warding planes uses

With the harness set to auto, the first installed runtime in this order is docked. The legacy adapter is optional and last: it is used only when nothing else is installed. Set agent.acp_backend to pick one explicitly.

How a harness gets added

One adapter in the runtime registry: the command line that starts the agent over stdio, which protocol family it speaks, a one-line login hint, and the binaries it needs on the path. That is the whole entry. The gateway, the channels and the schedules are shared code. What differs per harness is a short list of capability flags: whether it can share or steer a session, and whether it brings its own sandbox (the legacy adapter does, so Warding's own is not layered on top of it).

A harness adapts to the seams the first-class path already runs through. It cannot add a step, a flag or a failure mode to that path, and a harness that cannot fit does not land. What each one can do is then a matter of record, not of the registry: a cell above turns into a check only when a dated row exists on the verification log.
