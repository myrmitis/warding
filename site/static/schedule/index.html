Put your coding agent on a schedule

Cron jobs and a template gallery for the recurring work: the nightly build, the dependency bump, the stale-issue sweep. They run on your own machine, under the same policy as everything else. No run cap from us; your model plan's limits, and your vendor's terms for unattended use, still apply and may change.

Start from a template

The dashboard's Schedule page opens a gallery of 10 ready-made jobs for coding work. Picking one fills in the form; you review the prompt and the cadence and save it before anything runs. The ones marked Writes to your repos push branches, open pull requests or change issues, so they sit behind the same approval gate as any other tool call.

The week, on one page

The calendar view lays each job across the week, so a 02:00 build and a 06:00 dependency bump do not land on the same hour by accident. The executions view keeps each run's result.

Where you can create a job, on which harness

What a scheduled run is

  • Three kinds of schedule. An interval (at least 60 seconds), a five-field cron expression, or a one-shot at a set time.
  • A fresh agent session per job, reused across runs by default so a digest can refer to last night; set it to start clean each run for scanners and polling.
  • Under the same gate. A run's tool calls go through the approval ladder and the deny rules like any other session. A job can be set to auto-approve; a deny rule still refuses.
  • Results go where the job came from: the dashboard bell, and the chat conversation a job was created in. A failed run delivers its reason, not only a log line; repeated failures pause the job.
  • Skip dates and a time zone per job, for holidays. Daily and hourly jobs get a small random start delay; mark a job strict to fire on the minute.
  • A time limit per run: 30 minutes by default, up to 24 hours per job. Longer, checkpointed work belongs in the task runner.

Limits, stated plainly

  • No run cap from us; your model plan's limits still apply. We add no daily count. Your vendor's usage limits and its terms for unattended use are theirs, and they can change.
  • The box has to be on. A job fires only while the gateway is running. Nothing of ours runs in the cloud.
  • One harness for jobs. Every job runs on the harness docked for chat when it fires; switching is one setting.
  • Unverified overnight. No scheduled night has been recorded on any harness yet. The verification log gets the dated row when one is. Being verified
